# Memorimber UI調整・記録・レベル・共有機能 バックエンド実装引き継ぎ

## 1. この文書の位置づけ

この文書は `feature/issue-110-UI-adjust` で確定した画面仕様を、バックエンド担当がそのまま永続化・API化できる粒度にまとめた正本です。プロフィールのレベルと16種類の記録、共有グループのアイコン・表示設定・クイズ設定、共有クイズの集計を一体として扱います。

現在のフロント実装はUI確認を優先しており、次の値はまだブラウザ内だけにあります。

- レベル、活動累計、レベル到達時の基準値: `localStorage` の `memorimber-profile-level-state-v1`
- 共有グループのアイコン、写真表示設定、クイズ設定: `sessionStorage` の `memorimber-shared-group-presentation-v1:{groupId}`

これらは改ざん可能で、端末・ブラウザ・メンバー間で共有されません。DB移行時に正規データとして取り込んではいけません。信頼できる既存テーブルやイベント履歴から再集計し、履歴がない項目は後述の初期値方針を決めてください。

## 2. 変更してはいけない画面契約

バックエンド接続後も、次のUI挙動と文言を維持します。

### 共通・木・アルバム

- 各タブ上部の見出しは中央寄せ。
- 木タブの見出しは `MEMORIES / 思い出の木`。
- アルバムは `MONTHLY ALBUM / 月間アルバム`。クイズ・共有も同じ中央配置。
- 木タブのライトモードは、地面より上に薄い太陽と少し動く雲を表示する。
- ダークモードは、地面より上に控えめな月と満天の星を表示する。星は画面上部にも増やすが、Memorimberロゴやプロフィールアイコンの高さまでは侵入させない。
- 天候表現は四角い挿絵として浮かせず、木の背景へ自然になじませる。

### 共有一覧

- `参加中のグループ`、右上のスタイルカラーの丸いプラスボタン、グループ行を一つのまとまりとして見せる。
- 件数表示は置かない。グループ作成はプラス記号だけで表す。
- グループ行はグループ名の右側にメンバー名を薄く表示する。オーナーを先頭、その後は参加順。長い場合は省略する。
- 共有画面内でユーザー名を表示するときは、必ず直後に `Lv.4` 形式でそのユーザーの到達済みレベルを付ける。一覧、グループ設定、待機ルーム、クイズ順位、確認画面を含む。
- グループの丸いアイコンは、既定の人型アイコンの位置に表示する。

### 共有グループ詳細

- 一覧へ戻る操作と個別の共有思い出から戻る操作は、アプリ設定画面と同じ矢印に統一する。
- 大きいグループ名の左にグループアイコンを置く。
- グループ名の下に `N人のメンバー` と `N枚の写真` を同じ調子で並べる。
- 設定ボタンは歯車アイコンだけ。
- `みんなでクイズ` は説明用の黒い秒数・順位ブロックを置かず、簡潔なカードにする。
- `みんなでクイズ` と `共有された思い出` の間に薄い区切り線を置く。
- `共有された思い出` の件数表示を置かず、右側にスタイルカラーのプラス記号だけの共有ボタンを置く。見出し全体をカードで囲まない。
- 写真一覧自体は囲まない。写真表示設定が両方OFFなら正方形サムネイルを横3列にする。
- 共有解除の三点ボタンは小さくし、サムネイル画像内の右上に置く。
- 共有写真詳細は写真の縦横比を保ち、写真外の背景を画面背景と同色にして黒帯を出さない。
- `READ ONLY` や `所有者だけが編集できます` のような説明文は通常画面に表示しない。

### 共有グループ設定

- 全画面のスクロール可能な設定画面にする。
- 上から、丸いグループアイコン、大きい中央揃えのグループ名、メンバー、各設定項目の順。
- メンバー行の左は役割記号ではなく、その人の丸いプロフィール画像にする。画像未設定時だけ既定の人型アイコンを使う。
- オーナーのプロフィール画像だけ、左上に小さい冠を重ねる。冠は画像を隠さず、他メンバーには付けない。役割判定は必ずDBの `role='owner'` を使う。
- メンバー画像を押すと、そのグループ内のメンバープロフィールへ遷移する。
- アイコンとグループ名はアプリ本体のプロフィールと同様の操作感で編集する。
- 変更できるのはオーナーだけ。メンバーにも全項目と現在値を表示するが、薄い表示かつ操作不可にする。
- 既存の招待、メンバー削除、退出、グループ削除などの設定は失わない。
- `写真の表示` はラジオボタン風の独立チェック2個: `一言を表示`、`日付を表示`。既定は両方OFF（写真のみ）。
- `みんなでクイズ` は `ランダム` と `カスタム` を選べる。加えて `出題する思い出の数を投稿者でなるべく平等にする` の独立チェックを持つ。

### プロフィール

- レベル一覧の見出しは `レベルアップ`。
- 各項目は `レベル1 条件`、`レベル2 条件` … `レベル20 条件`。
- 色付きの現在位置は「今のレベル」ではなく、次に達成するレベル条件を示す。`現在地` という文字は出さない。
- レベル1条件は `思い出の記録をはじめる`。
- 記録は丸いアイコンを1行4個、全4行で並べる。初期表示はアイコンだけ。
- アイコンを押すと、そのアイコンが属する行の直下に説明欄を出し、それより下の行だけを押し下げる。
- 開いているアイコンをもう一度押すと説明欄を閉じる。同時に開ける説明は1個だけ。
- グループ経由で開く他メンバーのプロフィールは、自分のプロフィールと同じ配置にする。ただしプロフィール画像のカメラボタンと、ユーザー名の鉛筆ボタンは表示しない。
- 他メンバーのプロフィールでも、レベル横の矢印からレベル1〜20の条件を閲覧でき、16種類の記録アイコンを開閉できる。
- 左上にはアプリ設定と同じ丸い戻る矢印を置き、元の共有グループへ戻る。
- メンバープロフィール自体にもユーザー名直後の `Lv.N` を表示する。
- メンバープロフィールは「閲覧専用」という文字を出さず、編集操作そのものを存在させない。

現在のフロントでは、自分の行・自分のメンバープロフィールだけブラウザ内の実レベル・実記録・実アイコンを使います。他ユーザーはバックエンド値がないため既定アイコン、Lv.1、記録0のプレビューです。これはUI用フォールバックであり、本番仕様ではありません。

## 3. プロフィール「記録」16項目

`集計方式` が「現在値」のものは削除・退出・設定解除により減ってよい項目です。「累計」は成功イベントを一度だけ加算し、後から元操作を取り消しても減らしません。

| 行 | 記録キー | 画面で表す内容 | 集計方式 | 正規の判定元 |
|---:|---|---|---|---|
| 1 | `uploaded_photos` | 今まで残した思い出写真 | 現在値 | 認証ユーザーが所有する未削除 `memories` 件数 |
| 1 | `harvested_fruits` | 収穫した木の実 | 累計 | `memory_fruits.harvested_at` が初めて入った成功 |
| 1 | `correct_quiz_answers` | クイズ正解数 | 累計 | 通常・総集・木の実・復活・共有クイズの正解確定 |
| 1 | `active_months` | 思い出を残した月数 | 現在値 | 所有する未削除 `memories.memory_date` の `YYYY-MM` の重複なし件数 |
| 2 | `flown_petals` | 花びらを飛ばした枚数 | 累計 | 木の実収穫が成功し、花びらが生成・飛翔した時。1収穫につき1 |
| 2 | `revived_faded_memories` | 消えかけた花びらを復活させた枚数 | 累計 | 消えかけた花びらのクイズ後、花びらを戻す処理が成功した時 |

| 3 | `joined_groups` | 参加中のグループ数 | 現在値 | 現在の `shared_album_members` 件数（オーナーとしての所属も含む） |
| 3 | `created_groups` | 作成したグループ数 | 累計 | グループ作成成功。後から削除しても減らさない |

画面文言の語順は `lib/profile-data.ts` を正とし、0件も隠さず表示します。`connected_people` はプロフィールの公開フォロー数ではなく、現在所属している共有グループ内のユニークな相手数です。

### 降格禁止と写真進捗

- `achieved_level` は単調増加。写真、手紙、グループ等を削除しても絶対に下げない。
- 写真だけはレベルをまたいで累積・繰越する。
- 画面の分子は `現在の未削除写真枚数 - 現在レベル到達時の累計写真閾値`。0未満や分母超過を丸めない。
- 例: レベル10を88枚で達成後に1枚削除すると `-1/15`。
- 例: レベル10で写真120枚、追加条件待ちなら `32/15`。
- その状態でレベル11へ上がると、レベル11の累計閾値103枚が基準となり `17/15`。
- バーの見た目だけ0〜100%に収め、数値は生値を返す。

### 追加条件の開始基準

写真以外の追加条件は、必ず直前レベルへ到達してその条件が有効になった後から数えます。過去の活動を流用しません。写真進捗が負数でも追加活動は進みます。

条件が有効になった瞬間の対象活動累計を `baseline` として保存し、`current_total - baseline >= target` で判定します。同じイベントでレベルが上がり、次のレベルも同じ種類の活動を要求する場合、昇格直後の累計を次のbaselineにするため、同一イベントは次条件へ流用されません。

### 昇格トランザクション

1. ユーザーの進捗行を `FOR UPDATE` でロックする。
2. `user_id + event_type + source_event_id` の一意イベントをINSERTする。既存なら何もしない。
3. 新規イベントのときだけ累計を加算する。
4. 現在の未削除写真件数をDBから求める。
5. `achieved_level + 1` の条件を評価する。必要なbaselineがなければ現在累計で作る。
6. 写真と追加条件の両方が成立すれば1レベル上げ、連続昇格できる間は繰り返す。
7. `achieved_level` を下げるUPDATEは用意しない。

## 5. 共有グループ設定の永続化

現在 `components/shared-group-presentation.tsx` が保持している次の値を、全メンバー共通のDB値へ移します。

| DB/APIフィールド案 | 型・既定値 | 制約 |
|---|---|---|
| `icon_path` | `text null` | Storage内のオブジェクトパスだけを保存。data URLや公開URLは保存しない |
| `show_caption` | `boolean not null default false` | `一言を表示` |
| `show_date` | `boolean not null default false` | `日付を表示` |
| `quiz_mode` | `text not null default 'random'` | `random` または `custom` |
| `balance_quiz_contributors` | `boolean not null default false` | 投稿者均等モード |
| `quiz_month_count` | `smallint not null default 0` | カスタム時0〜10 |
| `quiz_photo_to_caption_count` | `smallint not null default 5` | カスタム時0〜10 |
| `quiz_caption_to_photo_count` | `smallint not null default 5` | カスタム時0〜10 |
| `quiz_seconds_per_question` | `smallint not null default 5` | 3、5、10のみ |

カスタム時は3方式の問題数合計を必ず10にします。ランダムは既存どおり合計10問・1問5秒をサーバーの正規値とし、以前保存したカスタム値が残っていてもランダム開始時には使いません。

アイコンと設定の更新はオーナーだけ許可し、SELECTは全メンバーに許可します。メンバー画面で薄い現在値を表示するため、非オーナーにも値そのものは返す必要があります。

### グループアイコン

- 入力はJPEG、PNG、WebP、最大5MB。
- フロントの現在のプレビューと同じく中央を正方形に切り出し、256×256程度のWebPを推奨。サーバーでもMIME・実画像・寸法・容量を再検証する。
- 専用のprivate bucketを作り、例として `{group_id}/icon-{uuid}.webp` に保存する。
- DBには `icon_path` のみ保存し、表示時に短命の署名URLを返す。
- 読み取りは所属メンバー、追加・置換・削除はオーナーだけ。
- 置換は「新規アップロード → DBパス更新 → 旧オブジェクト削除」。途中失敗時の孤児ファイルを再試行キューで掃除する。
- グループ削除時はアイコンも削除する。既定アイコンの場合は `icon_path=null`。
- 同じアイコンを共有一覧、グループ詳細の名前左、設定画面上部で使う。

### メンバーのプロフィール画像・レベル・記録

- `profiles.avatar_url` は現在どおりprivate Storageのパスとして扱い、APIレスポンスでは署名済みURLへ変換する。
- 共有メンバー一覧は、表示名に加えて `avatarUrl` とサーバー確定の `achievedLevel` を返す。
- 共有クイズの参加者一覧と順位にも同じ `avatarUrl`、`achievedLevel` を返し、すべてのユーザー名直後に `Lv.N` を描画できるようにする。
- メンバープロフィール取得は、16記録、到達レベル、写真進捗の生の分子・分母、次条件を返す。本人用プロフィールAPIと同じ集計関数を使い、別実装にしない。
- 呼び出し元と対象ユーザーが、URLで指定した同じ共有グループの現メンバーであることをサーバーで確認する。どちらかが退出した後は閲覧不可。
- メンバープロフィールの取得は集計情報の閲覧だけで、名前、画像、進捗、記録を変更する権限を一切与えない。

## 6. 共有クイズの確定仕様

### ランダム

- 現在の仕組みと同じランダム10問、1問5秒。
- 問題素材が10件未満でも繰り返して必ず10問作る。
- 同じ素材を繰り返す場合は、可能な限り前回と異なる方式にする。
- 一部の素材だけが3〜4問、他が1問になる偏りを避け、素材ごとの使用回数差を最大1に近づける。

### カスタム

- 方式は `いつか`、`写真から一言`、`一言から写真`。
- 各方式の問題数を0〜10で選び、合計は必ず10。
- 全問題共通の制限時間は3秒、5秒、10秒から選ぶ。
- クライアントのhidden inputは信用せず、開始RPC内でグループの保存済み設定を読み、問題計画を検証して確定する。

### 投稿者均等モード

1. そのセッションのクイズ参加者だけを対象にする。
2. 参加者ごとの、そのグループへ共有した有効な思い出数を数える。
3. 0枚の参加者は母集団から除外する。
4. 1枚以上の参加者の最小投稿数を `m` とする。
5. 各対象投稿者から `m` 枚ずつランダムに抽出し、その集合だけを問題素材にする。
6. 素材より問題数が多い場合も10問は維持し、方式変更とラウンドロビン選択で偏りを抑える。
7. 対象素材が0件なら開始せず、現在のフロントと同じ日本語エラーを返す。

現在のフロント用SQL `supabase/migrations/20260907010000_configurable_shared_quizzes.sql` は、3/5/10秒と追加方式を扱うための未適用候補です。環境へ適用する前に、上記の「保存済み設定をサーバーが読む」方式へ合わせてレビューしてください。

## 7. 推奨DB構成

既存の `profiles`、`memories`、`memory_fruits`、`shared_albums`、`shared_album_members`、`shared_album_memories`、`shared_quizzes` 系は維持します。進捗は次の分割を推奨します。

### `profile_progress`

- `user_id uuid primary key references auth.users on delete cascade`
- `achieved_level smallint not null default 1 check (between 1 and 20)`
- `created_at`, `updated_at`

### `profile_activity_counters`

- `user_id uuid`
- `metric text`
- `value bigint not null default 0 check (value >= 0)`
- 主キー `(user_id, metric)`
- ここには累計項目と、レベル判定に必要な `random_quiz_challenges`、`fruit_quiz_correct_answers`、`friend_quiz_sessions`、`print_attempts`、`saved_album_letters` も保存する。
- 現在値5項目（写真、活動月、所属グループ、接続人数、デザイン数）は原則クエリで算出し、キャッシュする場合も正規テーブルから再構築可能にする。

### `profile_activity_events`

- `user_id uuid`
- `event_type text`
- `source_event_id text`
- `amount integer not null default 1 check (amount > 0)`
- `occurred_at timestamptz not null default now()`
- 必要なら監査用 `metadata jsonb`
- 主キーまたは一意制約 `(user_id, event_type, source_event_id)`

`source_event_id` は、収穫ならfruit/memory ID、問題正解ならquiz session + question index、共有なら共有処理ID、グループ作成ならgroup IDなど、同じ成功を再送しても同一になる値にします。バッチ共有はイベントamountを成功INSERT件数にするか、共有行ごとに1イベントにします。

### `profile_level_baselines`

- `user_id uuid`
- `target_level smallint check (between 2 and 20)`
- `metric text`
- `value bigint not null check (value >= 0)`
- 主キー `(user_id, target_level, metric)`

レベル条件表はアプリ定数でもよいですが、フロントとサーバーに二重定義せず、APIが表示文言と進捗を返す形を推奨します。

## 8. API/RPC契約

### プロフィール取得

最低限、次を1回で返します。

```json
{
  "achievedLevel": 10,
  "photoProgress": { "value": -1, "target": 15 },
  "nextLevel": 11,
  "nextCondition": { "label": "ランダムクイズに挑戦する", "current": 0, "target": 1 },
  "records": {
    "uploadedPhotos": 87,
    "harvestedFruits": 12,
    "correctQuizAnswers": 24,
    "activeMonths": 8,
    "flownPetals": 12,
    "revivedFadedMemories": 2,
    "wordRecallReveals": 19,
    "goldenFruits": 1,
    "joinedGroups": 3,
    "createdGroups": 1,
    "connectedPeople": 7,
    "sharedQuizChallenges": 5,
    "sharedQuizWins": 2,
    "endlessQuizQuestions": 31,
    "sharedMemories": 9,
    "designedMemories": 4
  }
}
```

`nextCondition.label` 以外の内部条件説明は返さなくてもよく、少なくとも画面には表示しません。数値はすべて非負整数ですが、`photoProgress.value` だけ負数・target超過を許します。

### グループメンバープロフィール取得

推奨経路は `GET /api/shared-groups/{groupId}/members/{userId}/profile`、または同等の認証済みRPCです。レスポンスは本人用プロフィール取得と同じ進捗・16記録に、次を加えます。

```json
{
  "userId": "uuid",
  "displayName": "メモリさん",
  "avatarUrl": "短命の署名URLまたはnull",
  "role": "owner",
  "canEdit": false,
  "achievedLevel": 4,
  "photoProgress": { "value": 2, "target": 10 },
  "records": { "uploadedPhotos": 15 }
}
```

- `records` は実際には16キーをすべて返す。省略値をフロントで0と解釈させない。
- `canEdit` はグループ経由画面では本人を開いた場合も `false`。編集したい場合は本体のプロフィールへ移動する。
- 存在しない対象、対象がグループ外、呼び出し元がグループ外の場合は、所属情報を漏らさない同じ404応答にする。
- 署名URLの期限切れだけを更新できる軽量再取得、またはページ再取得を用意する。

### イベント記録

- サーバー成功処理に付随するイベントは専用の汎用公開APIを通さず、同じDBトランザクションで記録する。
- クライアントでしか確定できない `print_requested` と `word_recall_revealed` は、認証済みRPCへ冪等キーを送る。
- 印刷はボタン押下で確定し、PDF生成やOS印刷ダイアログの結果を待たない。
- クライアントイベントは許可リスト、入力長制限、レート制限を設ける。レベルはサーバーが再評価する。

### 共有グループ取得・更新

- 一覧レスポンス: group ID、name、署名済みgroup icon URL、オーナー先頭のメンバー表示名・署名済みプロフィール画像・到達レベル。
- 詳細レスポンス: 上記に加えmember count、photo count、全設定、`canEdit`。
- 更新はグループIDと完全な設定payloadを受け、オーナー権限をDBで検査する。
- メンバーにも同じ設定値を返すが、更新RPCは拒否する。

## 9. RLS・権限・整合性

- プロフィール進捗・活動イベント・baselineは本人だけSELECT可能。直接INSERT/UPDATE権限は与えず、検証済み `security definer` RPC経由にする。
- `security definer` は `set search_path = ''`、完全修飾名、必要最小限のEXECUTE権限にする。
- 共有設定とアイコンは所属メンバーがSELECT可能。UPDATEは `shared_albums.owner_id = auth.uid()` のみ。
- `profiles` 全体へ広いSELECT権限を追加しない。共有メンバー情報とプロフィール閲覧は、同一グループの現メンバーであることを検査する `security definer` RPCまたはサーバーAPIから、必要な表示項目だけ返す。
- メンバープロフィールAPIが返してよいのは、表示名、署名済みアイコン、グループ内役割、レベル進捗、16記録だけ。メール、Authメタデータ、Storageパス、baseline、イベント履歴は返さない。
- メンバー数、写真数、接続人数、ランキングはクライアント申告を使わずDBから求める。
- 共有クイズ1位はセッション完了後の確定standingsから一度だけ記録し、参加者1人以下なら記録しない。
- グループ作成・招待承認・写真共有・解除・退出は既存の原子的RPCとRLSを維持する。

## 10. 既存ユーザーの移行方針

1. 新テーブル・共有設定列・アイコンbucketとRLSを追加する。
2. 全プロフィールへ `achieved_level=1` の行を作る。
3. 写真、活動月、収穫済み木の実、金の木の実、所属グループ、接続人数、共有中写真、個別デザイン数は既存DBから再集計する。
4. 既存のクイズ正解、花びら表示、グループ作成累計、印刷、手紙保存など、履歴が存在する分だけ再計算する。
5. 履歴がない累計はブラウザ値を信用せず0開始、リリース日時以降のみ計測、またはプロダクト判断による一律補償のいずれかを明文化する。
6. 再集計値から初回レベルを機械的に20まで上げない。過去活動のbaselineをどう扱うかを決め、テストユーザーで確認する。
7. API切替後に `memorimber-profile-level-state-v1` と `memorimber-shared-group-presentation-v1:*` の読み書きを削除する。
8. 旧ブラウザ状態がAPI値へ上書きされないE2Eテストを追加する。

## 11. 受け入れテスト

### 記録

- 初期状態で16アイコンだけが4×4に並び、説明は閉じている。
- 各行のアイコンを開くと説明がその行の直下に出て下段だけが移動する。
- 同じアイコンを再タップすると閉じ、別アイコンでは説明が切り替わる。
- 接続人数は自分を除外し、同じ相手と複数グループで同席しても1人。
- 1人のみんなでクイズで1位記録が増えない。2人以上の確定1位だけ増える。
- 写真3件一括共有の成功で共有枚数が3増え、再読込や再送では二重加算しない。
- 個別アルバムデザインの保存・解除でデザイン済み現在値が正しく増減する。

### レベル

- 写真削除後も到達済みレベルが下がらない。
- 写真分子に `-1/15`、`32/15`、昇格後の `17/15` を表示できる。
- 追加条件が有効になる前の活動を算入しない。
- 写真を先に超過した状態では、追加条件成功直後に即昇格する。
- 同じ成功イベントの再送・Strict Mode・リロードでカウンターが増えない。
- レベル20は写真238枚到達だけで昇格する。
- 内部の謎解き条件やイベント名がユーザー画面へ露出しない。

### 共有

- オーナーが変更したアイコン・写真表示・クイズ設定を別端末のメンバーが同じ値で閲覧できる。
- 非オーナーは現在値を見られるが、UI・API・直接SQLのすべてで変更できない。
- 両方OFFは写真のみの正方形3列。一言・日付の各組み合わせが全メンバーで同じ。
- アイコン置換中の失敗でDBとStorageが不整合にならず、旧アイコンまたは新アイコンのどちらかが正常表示される。
- 投稿者均等モードは0枚の参加者を除外し、正の最小投稿数ぶん各投稿者から採る。
- 素材が10未満でも10問、素材使用回数と方式が可能な範囲で均等。
- カスタムは方式合計10、制限時間3/5/10以外をサーバーが拒否する。
- 設定画面は小さい端末でも最下部までスクロールできる。
- メンバー行は全員が丸い本人アイコンになり、オーナーだけ左上に小さい冠が付く。
- アイコンから同じグループのメンバープロフィールを開き、戻る矢印で元のグループへ戻れる。
- メンバープロフィールにはカメラ・鉛筆がなく、レベル条件と16記録の閲覧操作は本体プロフィールと同じ。
- 共有一覧、設定、待機ルーム、順位、確認画面、メンバープロフィールの全ユーザー名にサーバー確定の `Lv.N` が付く。
- グループ外ユーザーがURLを直接入力しても、メンバーの画像・レベル・記録を取得できない。
